# Auto Digger

Auto Digger is a desktop music discovery tool. A digging session finds random Discogs releases matching optional label, year, genre, style, artist, release-title and release-type filters. Discogs calls subgenres styles. Release types, genres and styles are searchable multi-selects: match any selected value within each field and combine the fields with AND. Style suggestions follow the union of selected genres using a versioned Discogs reference snapshot. Changing genres clears known incompatible styles; clearing all genres restores the complete flat style vocabulary. Styles missing from the historical hierarchy can be entered explicitly without guessing their parent. Applied filters are distinct from draft edits. Year accepts a single four-digit year or an inclusive ascending range passed directly to Discogs. Named filter presets and the last valid draft are stored as a validated SQLite metadata snapshot, independently of crates and appearance preferences. This reuses the existing preferences-store pattern of Zod validation and SQLite UPSERT.

A release is a specific Discogs pressing, identified by release ID. Release types include albums, EPs, singles, compilations and other Discogs format descriptions. No selected type means all releases, including unclassified releases. Digging avoids repeating release IDs within a session, verifies that loaded metadata matches any selected type and stays within Discogs' accessible search window. Changing applied criteria, explicitly resetting or reconnecting starts fresh.

A crate is a named local playlist of whole releases, distinct from a Discogs collection or wantlist. Each crate preserves insertion order and unique release IDs. Track picks and personal tags belong to that crate membership. Shared Discogs metadata stays separate. The main process persists the catalogue in SQLite and imports the original JSON crate once with a backup. Saved metadata and YouTube links can be reopened after restart without connecting Discogs. The active crate ID is a device UI preference, restored after restart. Without a saved choice or after that crate is removed, a populated crate is shown when available; explicit empty selections remain respected. It does not store credentials or audio.

YouTube and Soulseek are audio providers. Each attached video is a distinct YouTube source, and several sources can map to one Discogs track. Automatic video matching uses unambiguous complete titles; the user can correct assignments or keep the video title. yt-dlp and FFmpeg extract MP3, with best effort Discogs ID3 and artwork. The ID3 genre field contains Discogs styles, without the broad Discogs genre. The same tagging policy applies to Soulseek MP3s. YouTube sources retain their release/video identity and can be corrected offline without redownloading.

Soulseek uses a separately installed slskd API. YouTube and Soulseek are selected together under Audio sources. Choosing Soulseek shows compact search accordions for the release title and every track. Opening a row starts its editable search above a compact, scrollable table. Release searches suggest a Discogs track independently for each filename; ambiguous files remain unassigned until corrected. Punctuation becomes spaces while the catalogue title stays intact. Public files and private counts remain distinct. A download selects a public match issued by the main process and tied to the current connection settings. slskd owns the peer transfer; Auto Digger copies the completed file into its library, preserving the slskd copy. Soulseek identity includes release, peer, remote file and size, with explicit provenance. Original audio encoding is retained; non-MP3 embedded tags stay unchanged while Discogs metadata is indexed. The API key uses OS encryption and never returns to the renderer. The completed-downloads folder must be visible on this computer, including Docker host mappings.

Saved audio lives in Music/Auto Digger by default. The bottom player controls local audio, persists independently of browsing or Discogs connection and can reopen downloaded tracks after restart. Audio must be downloaded before local playback. Source rows use fixed-width icon controls with inline measured progress and cancellation; queued activity remains available in Downloads. No embedded YouTube playback or temporary preview transport remains.

A connected account means Discogs verified a personal token for the current app session. Decrypted tokens stay in main-process memory; an OS-encrypted credential is remembered on this device and verified again on launch. Disconnect forgets that credential and clears the account, loaded record, search results and digging history, while the saved crate persists.

Phases 1 through 6 cover desktop foundation, connection/metadata, filtered search, random discovery, YouTube playback and local crate persistence. Cloud sync and export are outside this prototype. Native preview installers use electron-builder, with an included runtime for the MCP entry and separate audio-tool prerequisites. Dedicated Crates, Downloads and Settings sections share the bottom player with the digging desk. Store links open exact Discogs sellers or artist/title searches; search results are not verified recording matches.

SQLite also indexes downloaded metadata and recorded directories. Sidecars support import/recovery and are not required for indexed playback. Unavailable destinations and missing audio affect individual rows. Settings opens from a cog at the navigation's right edge; material/accent are separate from appearance mode. Download organisation uses an editable relative path with source, genre, subgenre, year, label, artist and release placeholders. Subgenre uses the first Discogs style. New setups use <source>/<genre>/<subgenre>/<year>, while saved layouts remain unchanged. The reference stays visible, the preview updates while editing, and saving is explicit. An empty template keeps files together. Legacy layouts keep their behaviour until edited. Genre and label use the first Discogs value, missing values use Unknown folders, and release folders include the pressing ID. Destination/layout changes apply to future downloads without moving existing audio.

A download job is an explicit commitment to save one audio source for a release. The main process runs a bounded serial queue with measured provider progress and stage-only conversion/tagging. Cancellation cleans staging; committed files remain indexed. Retry preserves completed work and pending-source uniqueness. Whole-release saving uses the source-row assignments, makes missing/ambiguous tracks explicit and chooses at most one source per track. Pending queue history is in memory; durable audio is separate.

Downloads presents one searchable track list. Current jobs and durable tracks share source identity, so completed history does not duplicate files. The latest relevant activity appears inline with cancellation/retry, while source-page history remains available. The app uses flat section surfaces and dividers rather than nested cards; tagging notes are disclosed on demand.

Mix research is an opt-in local MCP workflow. An AI host supplies a sourced mix tracklist and recording-match judgment; the app verifies Discogs release IDs, stores named crate memberships/picks/tags and retains source evidence with confirmed, candidate or unresolved certainty. Research is crate-owned SQLite data, distinct from Discogs metadata and downloads. A separate SDK stdio process forwards narrow operations to the running app without receiving its Discogs credential. Claude Desktop installs a locally exported MCP bundle containing that helper and its dependencies. Other local clients use the included Electron runtime in Node mode. Access is disabled at startup and revocable in Settings. Research uses the same optional release-type filters and remains independent of the random digging session.
